## Metadata contract

`captureContext()` in `src/svartaksi/svartaksiRuntime.tsx:2290` fills
`PerformanceEnvironment` with runtime defaults, and four of its fields are placeholders
rather than measurements:

| Field | Runtime value | What it actually means |
| --- | --- | --- |
| `scenarioId` | `'runtime-debug'` | No scenario was selected; the harness must overwrite it. |
| `buildRevision` | `'runtime'` | Not a revision. Record `git rev-parse HEAD` by hand. |
| `warmupDurationMs` | `0` | Not "no warmup"; simply unset. |
| `sampleDurationMs` | `0` | Not "no samples"; simply unset. |
| `rendererKind` | `'unknown'` | Deliberate. `captureRendererIdentity` reads the unmasked strings when `WEBGL_debug_renderer_info` is exposed, but ANGLE and browser privacy settings make the string ambiguous, so classification is the operator's call. |

The plan's ruling on these is a documentation rule, not a code change:

> Preserve raw JSON unchanged and store corrected run metadata in the baseline Markdown or
> a sidecar JSON. Runtime defaults (`runtime`, `runtime-debug`, zero durations, unknown
> renderer kind) are not verified metadata.

So `captureContext()` is left exactly as it is. The raw export stays raw; the corrections
live here. Record, per run:

- revision (`git rev-parse HEAD`) and whether the tree was dirty (attach `git diff`)
- browser name and version; GPU as reported, plus the operator's **verified**
  hardware / software / unknown ruling and how it was established
- power mode (mains vs battery, any OS performance profile)
- viewport size in CSS pixels, `devicePixelRatio`, and the quality tier and render options
- world location and heading, time of day, camera mode
- cache state: cold (first load of a tile set) or warm — **keep these in separate runs**

## Run protocol

1. `pnpm build`, then `pnpm exec vite preview --host 127.0.0.1 --port 7777`.
2. Open `http://localhost:7777/?perfCapture=1` on the target device. Confirm world data
   actually loads in preview before capturing. Never compare a `pnpm dev` run against a
   preview run — build mode must be identical across every run in a comparison.
3. Wait for the runtime *and* for world/intro completion. `bridge.ready` only means the
   runtime object exists; it does not mean the world has streamed in.
4. Warm up 20 s, then capture 10 s of foreground play.

```js
const bridge = window.__SVARTAKSI_PERFORMANCE__;
if (!bridge) throw new Error('Open with ?perfCapture=1');
await bridge.ready; // Runtime exists; separately wait for world/intro completion.
await bridge.start();
// Return focus to the game and perform the documented 10-second scenario.
// On completion, run in DevTools:
const raw = await bridge.stop();
copy(JSON.stringify(raw, null, 2)); // DevTools clipboard helper, not application code.
```

5. Save the raw JSON unchanged to `captures/<date>-<scenario>-<run>.json`. Put the
   corrected metadata beside it, in this document or a sidecar `.meta.json`.
6. Three runs per scenario. Inspect sample timestamps for focus or console pauses and
   **reject a contaminated run whole** — do not drop its worst frames.

## Sampler capacity

`createPerformanceCapture` defaults to `capacity: 1_800`
(`src/performance/performanceCapture.ts`), and the sampler is a ring: it retains 1,800
*frames*, not a time window. At 60 Hz that is ~30 s; at 165 Hz it is ~11 s, and a 30 s
scenario silently keeps only its tail.

Before summarising, check `endedAtMs - startedAtMs` against the intended duration.
`startedAtMs` is the timestamp of the first frame recorded after `start()`, and it is
**not** rewound when early samples are evicted, so a truncated ring still reports the true
capture start — the gap between that start and the oldest surviving sample is the tell. At
high refresh rates, either shorten the scenario or raise the capacity, and use the same
capacity for baseline and candidate.

## Scenarios

Three scenarios, to be pinned to real coordinates on the first hardware run. **The
coordinates below are placeholders and are marked as such**; the plan requires exact
starting coordinates and route landmarks taken from the actual run, not invented here.

| Id | Description | To be pinned |
| --- | --- | --- |
| `stationary-exterior` | Stationary exterior view after the intro completes; no input. | spawn coordinates, heading, camera mode, time of day |
| `bus-route-segment` | The same segment of the same bus route, riding, from the same stop. | route id, boarding stop, alighting landmark |
| `stream-boundary-drive` | Driving across the same world-stream boundary at a comparable speed. | start coordinates, heading, the boundary crossed, target speed |

`stream-boundary-drive` is the scenario that Task 2 is measured against; the other two are
controls that show whether a change moved anything it should not have.

## Statistics to report

From the raw export, using the sampler's existing nearest-rank semantics
(`nearestRankPercentile`, rank `ceil(p/100 * n)`):

- frame ms p50 / p95 / p99, min, max, and sample count
- counts of frames over 25 ms and over 50 ms
- render-budget scale min and max — **check this first.** A "faster" candidate that also
  shows a lower scale has bought its frames by dropping quality automatically, and is not
  an algorithmic improvement.
- renderer `calls` / `triangles` / `geometries` / `textures`
- scheduler worst slice and histogram

Read the last two honestly: renderer and build snapshots in `PerformanceCaptureSnapshot`
are the **latest** values seen, not per-frame histories and not peak counters, and the
scheduler diagnostics describe the current or most recent job only.

Choose the primary statistic before running the candidate. The plan's screening target is
≥10% improvement in the median of three paired runs — a screening target, not proof. If
run-to-run spread is comparable to the gain, report inconclusive.
